01 / System boundary

先定义问题，再谈架构

实时风险决策系统接收一条业务事件，在严格时延预算内补齐必要特征、执行策略，并返回可解释的决策；需要改变外部状态的动作通常转入异步链路。

Input

规范化事件

事件类型、主体标识、场景上下文、请求元数据和可选业务载荷。入口层首先完成校验、鉴权、限流和统一建模。

Output

决策与解释

允许、拒绝、复核或降级结果，以及原因码、策略版本、命中特征摘要和可选的后续动作意图。

Constraint

有限延迟预算

总时延不是一个统一超时值，而是入口、特征、策略和响应序列化之间的预算分配与抢占。

Boundary

同步判断，异步执行

同步链负责给调用方稳定答复；封禁、通知、审核等外部副作用通过消息链路解耦，分别治理可靠性。

建立统一语言

事件
一次需要判断的业务事实，例如访问、提交、交易或内容发布。
特征
用于判断的可计算事实；可来自请求、缓存、远程服务或实时聚合。
策略
把特征映射为决策的版本化逻辑，可以是规则树、评分模型或组合编排。
副作用
会改变外部状态的动作，应与实时响应的可用性目标分开设计。

03 / Synchronous decision

第一条应深入的链路：同步决策

这条链路最能检验一个人是否真正理解实时系统：它同时涉及 API 契约、超时传播、特征依赖、策略执行、降级语义和可观测性。

请求规范化

客户端或接入层把不同业务载荷转换成稳定的 RiskRequest，补齐请求标识、调用来源、截止时间和追踪上下文。

保护与路由

按场景选择逻辑集群或策略集合，先执行本地限流、熔断和参数校验。调用方的截止时间必须向下传播，不能在每层重新开始计时。

构建决策上下文

DecisionContext 持有不可变请求、可变特征快照、预算、策略版本和解释信息，避免参数在节点之间失控扩散。

按依赖收集特征

将特征依赖构造成 DAG：同层可并发，跨层按依赖等待；先求值低成本条件，再决定是否请求昂贵的远程特征。

策略求值

策略只读取已冻结的特征视图，产出决策、原因码和动作意图。运行时记录实际策略版本，而不是只记录“当前配置”。

响应与异步派生

同步响应遵守清晰的降级契约；非必要的日志、样本和副作用事件在响应前最小化，在响应后或异步通道完成。

async function decide(request: RiskRequest): Promise<Decision> {
  const budget = DeadlineBudget.from(request.deadline)
  const context = DecisionContext.create(request, activePolicyVersion())

  const route = routeTable.select(context.scene)
  const features = await featureDag.collect(route.requiredFeatures, budget)

  if (budget.exhausted()) {
    return degradationPolicy.for(context.scene).fallback("FEATURE_TIMEOUT")
  }

  const result = policyEvaluator.evaluate(route.policy, features)
  sideEffectPublisher.publishBestEffort(result.actionIntents)
  return result.toDecision()
}

为什么选择 fail-open

  • 误杀成本高于漏放成本。
  • 风险能力不是主业务完成的硬前提。
  • 可以通过原因码、采样和补偿链路追踪降级。

什么时候必须 fail-closed

  • 合规或资金安全要求禁止不确定状态继续。
  • 缺失特征意味着无法验证强约束。
  • 业务提供了明确的人工复核或延迟处理路径。
04 / Feature dependency lifecycle

特征依赖 DAG：计划预计算，请求复用

依赖计划通常在配置加载或版本刷新时预计算；请求只创建本次执行所需的局部状态，然后按不可变计划调度特征。把“图的结构”与“图的一次执行”分开，是理解性能和并发安全的关键。

声明直接依赖

每类特征通过元数据声明前置条件：计算特征引用表达式变量，聚合特征引用分组键和过滤条件，远程特征引用请求参数。此时得到的是边集合，而不是某个请求的执行结果。

确定场景根集合

从当前场景会使用的策略、规则树和绑定输出出发，收集直接需要的特征。不同场景可以共享全局定义，但只编译自己能触达的子图。

求传递闭包

沿依赖边向前递归，得到根特征的全部前置特征。构建期同时检查引用缺失、自依赖和环，避免把不可执行的图切换到在线流量。

编译执行计划

拓扑遍历可以生成线性后序表，也可以生成多个 stage：同一 stage 内的节点已满足前置条件，可按资源类型并发或批量执行。

发布版本化快照

以场景、租户和版本为键缓存完整计划，通过原子替换发布。请求开始后固定一个快照，避免执行中途跨越两个依赖版本。

执行请求局部状态

请求复用节点顺序和 stage，只新建结果表、未完成任务、等待信号、剩余预算和追踪信息；这些状态不能跨请求共享。

function compilePlan(version, roots, metadata): ExecutionPlan {
  const edges = extractDependencies(metadata)
  const graph = transitiveClosure(roots, edges)
  rejectMissingReferencesAndCycles(graph)
  return freeze({ version, stages: topologicalStages(graph) })
}

async function collect(context, planCache): FeatureSnapshot {
  const plan = planCache.get(context.scene, context.tenant)
  const state = RequestState.from(context.input, context.deadline)

  for (const stage of plan.stages) {
    await runReadyNodes(stage, state)
  }
  return state.freezeFeatures()
}
构建期与请求期的职责边界
阶段主要工作可共享主要风险
配置加载 / 刷新解析依赖、闭包、环检测、拓扑分层版本化执行计划错误计划被发布、构建过慢
正常请求选择计划、执行节点、等待异步结果只读节点定义与顺序并发放大、预算耗尽
条件按需模式先算条件，再选择预构建片段节点或分支计划片段合并去重、分支等价性
缓存缺失兜底同步构建或加载计划构建完成后共享首请求抖动、并发重复构建

为什么不在每个请求建图

  • 依赖结构随配置版本变化，不随请求载荷变化。
  • 闭包、环检测和拓扑分层会重复消耗 CPU 与内存。
  • 预计算让错误尽量在发布阶段暴露，也让线上计划可观测、可回放。

请求仍会动态做什么

  • 按场景与版本选择计划。
  • 根据低成本条件选择已编译的分支片段。
  • 创建结果、任务、等待和超时状态，并执行真正的特征计算。

三种容易混淆的“短路”

Branch pruning

分支级：可以节省整棵子树

条件按需执行中，父条件不成立时，只裁掉该分支的后代；已经进入执行集合的兄弟分支仍继续。该优化依赖开关已启用且预构建的分支计划完整。

Call predicate

调用级：只跳过当前节点

远程或聚合特征可配置自己的调用条件。条件为 false 时，局部调用谓词只跳过一个特征调用，不会自动取消其他已计划节点。

Request outcome

请求级：不能从 DAG 剪枝推出

普通调度器仍按 stage 或拓扑计划继续。某个分支条件为 false 并不等于整次决策立即返回 false；提前结束整个决策属于更上层的业务语义，需要单独设计。

Cold path

缓存缺失不等于常态

有些实现允许首个请求同步构建并回填计划。更稳妥的做法是发布期预热，并对相同键使用 single-flight，避免并发冷请求重复建图。

Lazy path

选片段不等于重建拓扑

条件分支可以先执行少量特征，再合并命中节点的预构建 stage。需要验证跨片段去重、阶段对齐以及按需结果与全量结果等价。

Small graph

区分临时依赖执行器

某些局部流程会按请求把少量依赖转成 latch 或 future。它重建的是一次调用的等待状态，不应与主特征图的版本化执行计划混为一谈。

Complexity

构建成本看实现细节

一次 DFS 或拓扑排序通常是 O(V+E)；如果每生成一层都重新扫描全图，深链可能接近多轮 O(V+E)。因此构建应脱离请求关键路径。

Interview answer

三十秒回答

“依赖结构不是每请求计算。配置加载或刷新时先从特征元数据提取边，从场景根特征求传递闭包，完成环检测和拓扑分层，再把执行计划按版本缓存。请求只选择计划并创建本次执行的结果、Future 和等待状态。例外是缓存 miss 可能触发同步兜底，以及条件懒加载会选择并合并预构建片段，但它们都不等于每次重新解析整张图。”

05 / Configuration lifecycle

配置不是文件：它是一条发布链

策略系统的难点通常不在“如何读取配置”，而在错误配置如何被拦截、多个实例如何收敛、版本如何观测，以及出问题时能否快速回滚。

编辑与静态校验

校验语法、字段类型、引用关系、循环依赖和高风险动作；不能把所有错误留给运行时发现。

生成不可变版本

发布生成独立版本和内容摘要，记录作者、审批、差异与发布时间。运行时只消费版本，不消费“正在编辑的草稿”。

灰度与预热

先让少量实例或影子流量加载新版本，预取必要字典和模型，并验证加载耗时、内存与结果差异。

原子切换

在进程内构建完整新快照，通过单一引用替换；请求开始时固定版本，避免一次决策跨越两个配置版本。

收敛观测

每个实例上报当前版本、加载状态和失败原因。控制面关注“目标版本”和“实际版本”的差距，而非只看发布成功。

回滚与保底

回滚指向上一个已验证版本；新版本为空、解析失败或不完整时保留旧快照，而不是把错误状态替换进运行时。

推送通知

传播快，但通知可能丢失或重复。适合用来触发拉取，不宜把完整配置可靠性绑定在一次通知上。

周期拉取

最终能自愈，但存在生效延迟和集中访问压力。常见组合是“通知加速 + 周期校准 + 随机抖动”。

06 / Asynchronous side effects

异步链路的核心不是“用了消息队列”

消息系统只提供传输能力。真正决定可靠性的，是生产确认、消费提交、幂等键、重试边界、死信处理以及下游是否支持重复调用。

生成动作意图

策略返回结构化 ActionIntent，包含目标、动作类型、决策版本、幂等键和有效期，不直接在策略节点调用外部系统。

可靠投递

如果“响应成功但消息不能丢”是强要求，应使用事务消息或 Outbox；如果动作可补偿，则可以选择更低成本的尽力投递。

幂等消费

消费者先以业务幂等键查询处理状态，成功后记录结果。幂等窗口必须覆盖消息最大重试与积压恢复周期。

分级重试

瞬时网络失败使用有上限的退避；参数错误和永久权限错误直接进入人工或死信处理，避免无意义重试形成风暴。

下游适配

动作适配器统一超时、熔断、审计和结果映射，让消费框架不依赖每个下游的协议细节。

对账与补偿

最终状态不能只靠消费日志证明。通过状态表或定期对账识别“消息成功但下游未生效”等不一致并补偿。

async function consume(intent: ActionIntent): Promise<void> {
  if (await idempotencyStore.isCompleted(intent.key)) return

  const lease = await idempotencyStore.tryAcquire(intent.key, intent.expiresAt)
  if (!lease.acquired) return

  try {
    const result = await actionAdapter.execute(intent)
    await idempotencyStore.complete(intent.key, result.receipt)
    await consumer.commit()
  } catch (error) {
    if (isPermanent(error)) await deadLetterQueue.send(intent, error.code)
    else throw error
  }
}
07 / Design mechanics

六个值得讲透的关键机制

面试回答不要停在定义。每个机制都应说明它解决什么问题、参考实现、付出的代价，以及继续追问时如何展开。

Availability

分层 fail-open

问题
依赖抖动可能拖垮主业务。
方案
按场景、特征和错误类型定义降级，不使用全局统一放行。
取舍
提高可用性，但扩大漏放风险，必须记录降级原因。
追问
哪些风险等级允许缺省？谁决定阈值？
Execution

特征依赖 DAG

问题
串行太慢，全部并发又浪费资源。
方案
显式声明依赖，同层并发，条件分支延迟加载。
取舍
降低尾延迟，但调度、取消和可观测性更复杂。
追问
如何处理循环依赖和共享特征？
Runtime

动态选链

问题
不同场景需要不同成本和风险模型。
方案
入口按场景选择编排模板和策略版本，节点保持小接口。
取舍
扩展灵活，但路由组合爆炸，需要配置校验与审计。
追问
如何证明一次请求实际走了哪条链？
Consistency

版本化缓存

问题
配置读取不能阻塞实时请求。
方案
后台构建不可变快照，前台通过原子引用读取。
取舍
读路径稳定，但跨实例只保证最终收敛。
追问
如何检测实例长期停留在旧版本？
Client

SDK 治理

问题
调用方容易各自实现超时、重试和降级。
方案
SDK 统一请求契约、截止时间、路由、保护和错误分类。
取舍
降低接入成本，但升级节奏和语言版本成为治理问题。
追问
服务端与旧 SDK 如何保持兼容？
Reliability

幂等而非幻想 exactly-once

问题
消息重复、超时重试和消费重平衡不可避免。
方案
稳定业务键、状态机、下游幂等和对账共同防重。
取舍
需要额外存储与清理，并处理进行中状态超时。
追问
幂等记录与外部动作如何保持原子性？
08 / Failure drills

用故障推演检验架构是否成立

高级面试更关注异常路径。回答顺序建议固定为：现象与影响范围、快速止血、证据定位、根因修复、长期防复发。

特征服务尾延迟上升

现象：总 P99 上升，超时降级率同步增加。

  1. 按特征拆分耗时与在途数。
  2. 取消预算外任务并启用缓存值。
  3. 检查并发放大、连接池与下游限流。
  4. 把非关键特征移出关键路径或延迟加载。

错误策略快速扩散

现象：命中率或拒绝率在发布后突变。

  1. 冻结后续发布并切回稳定版本。
  2. 按策略版本对比结果分布。
  3. 定位校验、灰度或审批缺口。
  4. 增加离线回放、阈值护栏和自动回滚。

实例配置版本不一致

现象：同类请求在不同实例得到不同结果。

  1. 查看实例版本分布和加载错误。
  2. 摘除无法收敛的实例。
  3. 重新触发拉取并验证内容摘要。
  4. 建立目标版本收敛率告警。

消息积压与重复消费

现象：动作延迟，扩容后重复量增加。

  1. 确认生产速率、消费速率与分区倾斜。
  2. 保护下游后再逐步扩容。
  3. 检查幂等键覆盖范围和状态超时。
  4. 按业务优先级分流积压并执行对账。

下游动作系统雪崩

现象：消费线程被慢调用占满，重试持续放大。

  1. 熔断并暂停非关键动作。
  2. 限制重试并隔离失败类型。
  3. 降低单消费者并发，保护下游恢复。
  4. 增加每动作独立线程池与速率预算。

降级被误当成正常放行

现象：总体成功率正常，但风险效果持续下降。

  1. 区分业务决策与异常降级结果。
  2. 对降级原因码单独计数和告警。
  3. 采样保存缺失特征与依赖错误。
  4. 把效果指标与系统可用性联合观察。

两分钟回答骨架

“这个系统解决的是在严格时延预算内，对业务事件完成实时风险判断。同步链路把请求规范化后构建决策上下文，按依赖 DAG 收集必要特征，再使用固定版本的策略生成结果；会改变外部状态的动作通过消息链路异步执行。架构上的主要取舍是可用性与风险效果、配置生效速度与一致性、消息吞吐与副作用幂等。出现特征超时或错误配置时，我们分别通过预算降级、版本回滚和收敛观测控制影响。至于我个人负责的部分，我会只讲自己实际设计、实现或处置过的内容。”

回答时要主动守住的边界

  • “使用消息队列”不能推出端到端 exactly-once。
  • “有缓存”不能推出跨实例强一致。
  • “支持灰度”不能证明实际发布流程执行了灰度。
  • “系统模块存在”不能替代你个人的真实工作范围。
  • 生产流量、延迟和收益数字只使用你能解释口径与来源的数据。
10 / Self check

十个问题检查理解深度

先独立回答，再展开提示。好的答案应该包含边界条件和失败路径，而不仅是术语定义。

为什么总超时不能简单平均分给每个特征？

特征有依赖、命中概率和业务价值差异。应按关键程度与成本分配预算，并让剩余预算随执行动态收缩；并行任务还需要可取消，避免请求返回后继续消耗资源。

fail-open 与“吞掉异常”有什么区别？

fail-open 是显式业务策略：只对允许的场景和错误类型返回降级结果，并携带原因码、指标与追踪信息。吞异常没有契约，也无法评估风险敞口。

特征 DAG 如何避免并发放大？

使用条件剪枝、请求内去重、跨请求缓存、全局并发预算和按下游隔离的线程池；同层可并发不代表所有节点同时启动。

为什么请求开始时要固定策略版本？

否则一次决策可能读取到两个版本的规则或字典，结果不可重现。固定版本还能让日志、回放和问题定位形成稳定证据链。

如何证明配置发布真正完成？

不能只看控制面“发布成功”。要观察目标版本、实例实际版本、加载结果、内容摘要和收敛比例，并对长时间未收敛实例告警或摘除。

消息消费者已经去重，为什么下游仍要幂等？

消费者可能在外部动作成功后、提交消息前崩溃；去重记录也可能过期或写失败。端到端可靠性需要每一条可重复边界都有防线。

什么时候需要 Outbox？

当业务状态变更和消息发布必须具有一致结果，且无法接受“状态已提交但事件丢失”时使用。代价是额外存储、转发器和积压治理。

如何区分系统成功率与风险效果？

系统成功率关注请求、依赖和延迟；风险效果关注命中、误判、漏判和后验结果。大量 fail-open 可能让技术成功率很好看，却让风险效果恶化。

策略错误时，为什么回滚通常比热修更可靠？

回滚指向已验证的不可变版本，操作路径短且结果可预测；在线热修会引入新的未验证差异。修复应在止血后重新走校验与灰度。

面试中如何区分系统事实与个人贡献？

先用“系统采用……”描述公共事实，再用“我负责……”限定自己的设计、编码、评审或故障处置范围；没有亲自完成的部分不使用第一人称功劳表达。

没有匹配的学习卡片

尝试更短的关键词，例如“缓存”“超时”或“幂等”。
