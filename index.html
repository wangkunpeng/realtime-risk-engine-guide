可解释决策系统：从请求到可执行计划

用一套独立设计，理解配置驱动系统的边界、并发、版本与故障处理

原创通用参考设计 · 教学稿

本指南独立构造了一套虚拟系统。组件名、协议、伪代码和示例均服务于教学，不对应任何组织的实际架构，也不声明某个生产系统已经实现这些能力。涉及容量、时限和阈值时，应通过自己的负载与业务要求确定。

CHAPTER 01

架构：把业务判断与运行环境分开

设想一个优惠资格服务：输入用户、活动与商品事实，输出可领取、需补充信息或不可领取，并可能生成后续任务。设计的起点是明确谁定义规则、谁提供事实、谁负责把结果交给调用方。

教学系统分为契约层、应用层、计划层、能力层和基础设施适配层。RequestGateway 理解传输协议，DecisionService 编排一次决策，PlanCompiler 把声明转换成计划，CapabilityRegistry 描述可调用能力。持久化、远程访问和消息发送放在适配层，通过应用层定义的端口接入。

依赖方向与数据流方向不同。请求数据可以从网关流入业务，业务又调用存储；代码依赖则指向稳定契约。业务需要一个读取事实的端口，无需认识某种客户端连接或某个配置系统。边界的价值应由替换成本与故障隔离验证，不能只数目录层数。

参考设计

端口先定义语义，适配器再选择技术

可替换性来自依赖契约的稳定，而不是把实现包在一个同名接口后面。端口必须说明成功、缺失和不可用各代表什么。

输入
一项业务需要的事实、允许使用的时间预算、事实的新鲜度要求，以及读取失败时可接受的业务行为。
输出
稳定的 FactReader、DecisionWriter 等应用端口，以及实现这些端口的适配器；应用层只处理领域结果和明确的失败类型。

运行分支与交互

01需求是纯业务判断

让函数接收已标准化的事实与计划，返回 Decision。将时间、随机选择和外部读取显式传入，便于复算同一个输入，而不是在判断深处隐式获取环境。

02需求必须访问外部能力

由应用层声明端口及结果类型，例如 Found、Missing、Unavailable；适配器负责把具体协议和异常翻译进来。缺失数据不能伪装成网络失败，网络失败也不能默认为业务上的否定事实。

03一个适配器需要替换

先运行端口契约检查：字段解释、空值、超时、重试和取消是否一致。通过检查后切换装配关系；不要求新旧系统拥有相同存储结构，也不把适配器特有选项扩散进领域对象。

04新增能力要求业务修改大量分支

审查扩展点是否放错位置。如果只是接入方式不同，应改适配器；如果输入含义和失败语义改变，应升级端口契约，不能用无类型参数袋掩盖领域变化。

interface FactReader {
  read(query, budget, cancellation): Found | Missing | Unavailable
}
class DecisionService {
  constructor(reader: FactReader, plans: PlanReader)
  decide(request): Decision
}

技术实现与取舍

接口数量本身不是目标。稳定业务语义与不稳定基础设施交界处值得设端口，只有一个简单纯函数的内部细节未必需要接口。每层应承担可单独解释和检查的责任。

适配器可共享连接与序列化工具，但不要让连接生命周期成为领域生命周期。组合根集中选择实现，使测试可以装配内存端口，也使一次替换不必重写核心决策。

失败时会发生什么

  • 返回 null 表示所有失败，会迫使上层猜测含义，最终把依赖异常误判成资格不满足。
  • 业务直接引用客户端异常和存储行结构，会把技术替换变成全链路语义迁移。
依赖倒置是否会让调用链更难追踪？

如果装配关系分散，确实会。把端口、实现选择和运行实例标识集中在组合根，并在诊断信息中记录实际适配器，既能保持边界，也能追到真实执行者。

何时应升级接口而不是兼容旧参数？

当字段意义、失败分类或可承诺的一致性改变时。仅增加可选展示字段可能保持兼容；把“未找到”改成“稍后可重试”则改变了调用方行为，应明确版本。

参考设计

RPC 契约与响应的唯一终结点

传输成功、业务允许和依赖完整是不同维度。网关负责把所有执行路径收束成一次终结，调用方才能可靠解释响应。

输入
带请求标识、业务输入、调用方预算与取消信号的请求信封；可能存在重复投递、字段版本差异或已经耗尽的预算。
输出
恰好一次尝试写出的终态响应：传输状态、领域决策、执行完整性和可复算版本分别表达；诊断原因可机器读取，避免只返回模糊字符串。

运行分支与交互

01信封无效或契约版本不支持

在接触业务依赖之前终结为输入错误，并指出可修正字段。请求标识进入诊断上下文，但不回显敏感原文；拒绝自动猜测会改变业务含义的字段。

02请求有效且剩余预算足够

固定版本并创建执行上下文，将可用预算分给排队、依赖与收尾。应用返回领域结果，由网关统一映射到响应，不允许深层组件直接操作传输观察者。

03超时、取消与正常完成发生竞争

用终结状态的原子转移选择获胜者。获胜路径关闭响应、触发清理，其他路径仅记迟到结果；不能在已经返回超时后再发送一个业务成功。

04发生未预期异常

在最终边界转换为稳定错误类别，并保留可关联诊断标识。业务是否允许继续由显式降级策略决定，不能把捕获异常等同于允许，也不能依赖异常文案解析行为。

finish(result):
  if terminal.compareAndSet(OPEN, CLOSED):
    response.write(mapResult(result))
    scope.close()
  else:
    diagnostics.recordLateResult(result.kind)

技术实现与取舍

响应同时包含 decision 与 completeness，使“允许且事实完整”和“按降级政策允许但事实缺失”可区分。调用方重试应依赖错误类别与幂等契约，而不是根据允许或拒绝猜测系统健康。

单一终结点减少重复回调，但不表示远端操作停止或副作用只发生一次。响应生命周期、计算生命周期和外部动作生命周期需要各自的状态机。

失败时会发生什么

  • 每个异常分支自己发送响应，容易出现重复终结、遗漏清理以及失败路径没有响应。
  • 预算只传给网络调用、不限制线程池排队，会让请求在真正发出远程请求前就已失去价值。
为何不把全部问题统一成一个错误码？

调用方需要知道是否修正输入、等待重试或接受领域判断。统一错误会把业务拒绝误当系统故障，也可能对不可重试动作反复重试。

一次响应终结是否意味着执行恰好一次？

不是。它只约束本进程对该响应通道的收束。请求可能重发，远端可能已执行，动作也可能在超时后完成，需要单独的幂等与状态查询协议。

CHAPTER 02

计划：把声明转换成可执行的依赖图

配置是面向编辑者的声明，执行计划是面向运行时的程序。PlanCompiler 负责在发布前解析、检查和组织工作，运行时只消费已经验证的计划。

一份活动规则可能引用库存、用户资格与预算分配。编译器先建立符号表，再验证依赖，再生成节点与边，最后生成可解释摘要。配置中能够表达的内容不应自动获得无限计算或任意外部访问能力；资源与权限也是计划的一部分。

参考设计

从原始声明到带不变量的计划

发布前应证明计划的基本结构成立。一个对象能反序列化，并不代表它引用的能力、类型与依赖关系可以执行。

输入
一组声明、能力目录、输入输出类型定义、表达式语言版本和资源约束；所有输入归属于候选版本。
输出
不可变 ExecutionPlan，包含依赖图、常量、已解析符号、能力签名和验证摘要；失败时返回定位到声明位置的诊断集合。

运行分支与交互

01声明能够解析但符号尚未解析

构建命名空间和符号表，区分请求事实、计算节点与外部能力。重复定义与歧义必须报错；不要让 Map 的最后一次覆盖决定业务结果。

02节点引用了另一个节点或能力

检查引用存在、类型可赋值、权限可用，且结果缺失策略明确。把转换规则编入计划，避免运行时临时把字符串当数值或把未知当否定。

03图结构与资源检查开始

检测环、不可达节点、没有终点的分支与不受约束的扇出。对纯表达式做受限的常量折叠；外部读取、随机与时钟相关节点不得在编译时偷偷执行。

04全部硬性校验通过

生成内容摘要和验证报告，冻结计划对象并交给候选版本存储。预热失败与语义验证失败分别记录；只有满足发布门槛的候选才可以成为当前版本。

compile(declarations, catalog):
  symbols = resolveNames(declarations)
  graph = typeCheckAndLink(symbols, catalog)
  rejectCyclesAndUnboundedWork(graph)
  return freeze(lowerToExecutionPlan(graph))

技术实现与取舍

编译前移错误发现，降低请求路径的图解析开销；代价是配置发布本身变成需要观测与回退的工程流程。验证报告应与计划内容绑定，不能复用另一份文本的旧报告。

部分未知依赖可以建模为动态输入，但必须有明确端口与类型。允许少量动态扩展不等于绕过完整性检查，否则编译产物只是换了格式的原始配置。

失败时会发生什么

  • 只检查图无环，忽略能力输出类型，会把错误推迟到节点执行时才出现。
  • 编译器读取不断变化的目录并混合不同版本能力，可能生成无法复现的计划；候选输入也需要固定视图。
为什么需要保存验证摘要？

它把“验证过什么”与“实际发布什么”关联起来，便于判断目录、语言或权限变化后是否必须重新编译，也让回放能够说明当时采用的契约。

无环是否意味着计划一定能结束？

不意味着。远程调用可能没有期限，节点可能运行无界循环，资源队列也可能永远等待；结构终止性与执行期限要分别约束。

参考设计

按需求建闭包，再对条件分支剪枝

按需执行需要保留“为什么需要这个节点”的信息。先确定必需结果，再延迟选择分支，可以减少无关读取而不改变业务语义。

输入
计划依赖图、请求选择的目标结果、条件表达式，以及每种事实在未知、缺失和失败时的分支定义。
输出
当前请求需要执行的子图和可解释的剪枝记录；未选择节点不占用执行资源，但仍保留在原始计划以支持其他请求。

运行分支与交互

01请求只需要部分结果

从目标向依赖反向求闭包，标记共享节点，去掉不影响这些结果的工作。仅用于审计的字段是否保留要显式决定，不能顺手删除必要证据。

02条件可以用已知纯事实确定

选择分支后扩展该分支的闭包，取消尚未启动的另一分支。条件节点与分支节点分开记录，便于解释为什么某个昂贵能力没有被调用。

03条件为未知或依赖失败

采用三值语义或明确兜底边，不把未知自动视为 false。若业务需要补充信息，就生成该结果；若允许继续，记录所依赖的降级依据。

04分支共享能力或包含外部动作

共享的纯计算按节点标识合并；外部动作只生成意图，不因推测执行而触发。已经开始的共享读取只有在没有其他消费者时才有资格取消。

技术实现与取舍

推测执行可以缩短延迟，却会增加无用读取与隐私访问范围。教学设计默认在条件确定后启动昂贵分支，是否推测应由可观测成本和业务价值决定。

剪枝改变执行集合，不改变决策规则。优化前后应对允许的输入域做语义等价检查，尤其覆盖未知事实、短路表达式和可空值。

失败时会发生什么

  • 把没有采集的值当成 false，会让剪枝优化悄悄改变判断结果。
  • 节点仅按能力名称去重，会把不同参数、不同版本或不同隔离域的读取错误合并。
为什么不能先把全部依赖并行发出去？

这会失去条件剪枝的资源收益，还可能访问业务没有必要获取的数据。只有纯、受控且收益明确的分支适合推测，副作用更不能混入推测读取。

如何解释“未执行”的节点？

区分目标不需要、条件排除、被上游失败阻断、预算不足和主动取消。这些原因不同，能够帮助复盘规则语义而不是误判为能力缺失。

CHAPTER 03

表达式：缓存的是带语义环境的程序

ExpressionStore 保存的不是一段文字的答案，而是特定语言与类型环境下的编译产物。同一文本的含义可能随函数目录、隔离域与编译选项改变，键设计必须覆盖这些变化。

先把解析缓存、编译缓存和执行结果缓存分开。解析缓存重用语法结构；编译缓存重用类型绑定后的程序；结果缓存还需要把业务输入、时效和读取语义纳入键。把这三者混称为“表达式缓存”，会使失效策略无法讨论。

参考设计

用语义指纹定义编译缓存键

正确的缓存命中意味着编译语义相同，而不只是字符串相同。键应绑定所有会改变程序含义的稳定版本。

输入
表达式文本、语言与编译器标识、输入类型模式、函数目录摘要、隔离域和会影响语义的编译选项。
输出
可复用的编译产物及其语义指纹；命中或失效理由可观测，不在请求日志中暴露表达式中的敏感常量。

运行分支与交互

01收到新的表达式声明

先解析为受限语法结构，再进行不会改变语义的标准化。空白可忽略，但字符串字面量和顺序敏感操作不能盲目重写；保存原文定位与规范结构的映射。

02准备查询编译缓存

组合规范结构摘要、语言版本、输入模式、函数目录摘要与隔离域。只有相关环境一致才允许共享；身份相同不意味着权限相同，权限变化也应通过明确版本进入环境。

03缓存命中且产物仍满足执行契约

取得不可变程序句柄，执行时传入本次请求变量。变量不写回共享产物；若编译器需要可变运行状态，将它放进独立执行帧。

04环境更新或内存压力要求回收

新环境产生新键，旧产物按引用和容量政策逐步回收。容量按估算重量而非只有条数计量；撤销权限等必须立即生效的变化需要单独的拒绝检查，不能仅等缓存自然淘汰。

key = fingerprint({
  normalizedSyntax, languageRevision, inputSchema,
  functionCatalogDigest, isolationDomain, semanticOptions
})
program = expressionStore.acquire(key)
result = program.run(new ExecutionFrame(requestValues))

技术实现与取舍

键包含更多语义会减少错误复用，也会降低跨版本命中率。可把语法解析产物与环境绑定程序分层保存，复用稳定部分，而不是为了命中率省略必要维度。

摘要用于索引并不消除碰撞可能。对高要求场景保留完整元信息进行命中校验，或采用能够接受的碰撞与隔离策略；摘要也不应被当作敏感文本的加密保护。

失败时会发生什么

  • 仅以文本作键，可能在函数签名变化后执行绑定到旧语义的程序。
  • 缓存产物混入请求变量，会造成跨请求污染；给缓存加锁只能缓解竞争，不能修正错误的对象所有权。
为什么业务版本不直接放进所有缓存键？

可以，但会降低不相关变化之间的复用。语义指纹应覆盖实际依赖：表达式只依赖某个函数子集时，可使用该子集摘要；正确性优先，再优化命中范围。

输入值需要进入编译缓存键吗？

通常编译缓存绑定输入类型而非具体值。若做值特化优化，特化条件就必须进入键；若缓存的是执行结果，具体输入与时效更是必需维度。

参考设计

并发冷编译：共享工作，不共享请求状态

冷编译可以采用按键合并工作，但等待者有各自预算。编译任务的寿命、缓存项的寿命与请求的寿命应分别管理。

输入
相同语义键上的并发获取请求、每个等待者的期限、编译资源预算和编译环境的不可变视图。
输出
成功时多个等待者共享同一不可变产物；失败时得到分类明确的编译结果，正在进行的占位项被可靠清理。

运行分支与交互

01键已存在成功产物

快速取得句柄并更新使用记录，不进入编译队列。产物已被驱逐但仍有请求持有时可继续安全执行，回收由句柄生命周期管理。

02键缺失且没有进行中的工作

原子安装一个代表编译结果的承诺对象，由获胜者提交编译任务。先限制全局及隔离域的并发编译，避免大量不同键一起冷启动耗尽处理器。

03同键已有编译任务

新请求加入等待但保持自己的截止时间。等待者超时只解除自己的订阅，不能无条件取消其他请求仍需要的编译；最后一个等待者退出后再根据预热价值决定是否终止任务。

04编译完成、失败或环境被撤销

成功时完成承诺并发布产物；语法错误可短暂保存为有界负缓存，资源异常采用退避；所有退出路径用 finally 移除进行中占位，并用身份比较避免删除后来创建的同键工作。

技术实现与取舍

按键合并防止同一个程序重复编译，全局限额防止不同程序同时编译；两个维度缺一不可。限制应覆盖排队内存、执行时间与产物体积，而不只是工作线程数。

恢复执行异常时先区分输入错误、依赖撤销与编译器问题。只对明确可恢复的类别重新编译，并把重试绑定到预算；对所有异常重编译会掩盖错误并放大负载。

失败时会发生什么

  • 失败承诺永久留在进行中表，会让后续请求永远复用一次暂时性故障。
  • 在全局锁内编译会让无关键相互阻塞；只对安装与移除占位做原子操作，把昂贵工作放到锁外。
为何等待者超时后不立即取消编译？

编译可能被其他请求等待，也可能值得作为预热继续完成。等待者拥有自己的订阅，编译协调器拥有共享工作的取消权，二者不能混为一谈。

负缓存与普通失败重试如何配合？

确定性语法错误可在声明不变时短暂复用诊断；资源不足与外部目录读取失败可能很快恢复，应退避并限制重试。缓存错误的依据是失败是否稳定，而不是异常名字相似。

CHAPTER 04

版本：构建一组能被请求固定的状态

“快照”应该是可验证的读取约束：请求从何处取得版本、哪些对象属于该版本、异步分支如何携带它。给缓存对象增加一个版本字段，并不能自动建立这种约束。

本教学设计使用 VersionBundle 作为不可变根，包含计划、能力目录、类型模式与相关决策参数。发布者在旁路构建候选，读者通过一次根引用获取固定视图。需要立即生效的撤销信息单独定义语义，避免把长期固定版本变成权限撤销障碍。

参考设计

用不可变根与请求句柄固定版本

一致性承诺的范围等于固定根实际覆盖的读取范围。所有参与一次判断的版本化读取，都必须经过同一个请求句柄。

输入
已经验证的候选 VersionBundle、当前发布根，以及进入系统的新请求；外部事实另有自己的新鲜度语义。
输出
一个固定版本的 RequestScope；其中的计划、能力描述和决策参数彼此兼容，旧请求可以完成，新请求使用后来发布的版本。

运行分支与交互

01候选版本构建完成

检查所有成员摘要和引用闭包，确认依赖的能力契约存在，并做有限预热。冻结对象图，禁止发布后向其中填字段；缓存懒加载状态放在版本外的协调器。

02发布新版本

比较预期父版本与当前根，原子替换根引用。并发发布冲突时重基或重新构建，不让较旧候选无条件覆盖较新版本；发布记录包含候选摘要和验证结论。

03请求或异步子任务开始

请求只获取一次根并创建句柄，所有版本化读取从句柄派生。异步任务显式携带句柄与预算，不能在线程池线程中重新查询当前版本。

04旧版本退出或发生强制撤销

在没有请求引用后释放旧根资源；长期任务受生命周期上限约束。若某能力必须紧急撤销，在执行边界查询独立撤销门，记录这是对固定快照语义的有意例外。

scope = RequestScope.acquire(versionStore.currentRoot())
try:
  plan = scope.bundle.planFor(request.intent)
  return executor.run(plan, scope)
finally:
  scope.release()

技术实现与取舍

固定版本降低中间态组合风险，却会让旧请求继续使用旧政策。必须明确可接受的旧版本寿命，以及哪些安全撤销可以中断旧请求；不能同时承诺无限期可复算与所有变化瞬时生效。

配置快照不意味着外部世界静止。库存与余额仍可能变化；需要事务、条件写或带版本事实来保护后续动作，不应把固定计划误当成固定业务数据。

失败时会发生什么

  • 请求持有旧计划，但能力读取又访问当前目录，会重新组合出未验证的版本集合。
  • 只替换根引用但根下集合仍可修改，会让旧请求看到发布后的变化；不可变性必须覆盖整个被承诺的对象图。
快照能保证同一输入永远相同结果吗？

它只固定配置与程序。结果还可能依赖外部事实、时间与随机性；可复算需要一并保存事实证据或受控种子，并定义隐私与保留期限。

为什么不直接给每个 Map 加锁？

单独锁不能保证跨 Map 组合相容，统一大锁又会把读取和发布耦合。不可变根把完整构建放到旁路，再用单次切换建立清晰读取边界。

参考设计

变更传播：通知是线索，版本才是事实

变更事件可以驱动刷新，但事件重复、延迟和丢失都不应破坏最终收敛。消费方应围绕目标版本构建与确认，而不是盲目执行通知次数。

输入
带目标摘要、父版本和变更范围的通知，配置源的可读取版本，以及本地已经成功发布的版本标识。
输出
经过验证后发布的新根，或明确保留旧根的失败状态；传播进度可以按版本追踪，重复事件不引发重复发布。

运行分支与交互

01收到重复或较旧通知

比较本地已应用摘要和版本关系，忽略已完成目标。版本标识不能单纯依赖机器时钟，跨源变更使用明确父子关系或可比较的修订协议。

02收到可读取的新目标

合并同目标的重复请求，并依据依赖索引确定受影响计划。局部重建仍产出完整候选根，未变化成员复用不可变对象，避免把局部更新变成半份可见状态。

03目标暂时不可读或中间版本缺失

采用有界退避，并从权威源重新确认目标；如果协议允许跳过中间版本，可直接构建完整新版本。周期对账比较已发布摘要，补偿没有收到的通知。

04构建或校验失败

保留当前根，记录目标、失败阶段与依赖证据，不发布部分结果。修正输入后可重新构建同一目标；成功切换后再确认传播完成，不能把收到消息当成已生效。

技术实现与取舍

同步通知容易理解，但下游构建成本会阻塞上游；异步通知降低耦合，却需要去重、对账和进度观测。本设计选择异步线索加版本对账，把正确性放在可读取目标与完整发布上。

依赖索引优化重建范围，不应该成为唯一正确性依据。目录结构变化或索引不完整时回退完整构建，资源成本增加比静默漏更新更容易发现和控制。

失败时会发生什么

  • 只在收到事件时刷新，没有周期对账，一次丢失通知可能造成长期不收敛。
  • 监听回调逐个修改线上对象，即使每次修改都成功，也可能短暂暴露从未验证过的组合。
配置源发送成功能证明所有实例生效吗？

不能。至少要区分发送、接收、构建、验证与发布。生效证明应来自目标实例对已发布版本的报告，并覆盖所需实例集合。

局部构建是否与整组快照冲突？

不冲突。可以只重新计算受影响成员，再将未变化的不可变成员组合成完整候选；关键是对读者只发布完整根，而不是逐项暴露计算进度。

CHAPTER 05

能力：注册契约与结果映射

同一个“读取资格事实”可以由本地数据、远程服务或组合计算提供。能力目录应描述业务可依赖的语义，而非只提供一个可以反射实例化的类名。

CapabilityRegistry 保存描述与工厂，CapabilityAdapter 负责技术调用。运行时按已固定目录解析执行者，并把原始响应转成统一的事实结果。映射是可审查的程序：状态、字段缺失、单位与时区都可能改变决策。

参考设计

描述、装配、调用和结果映射分别检查

注册成功只说明目录知道一个能力，不能证明它已可用或结果可用于判断。解析、初始化、调用与映射都有独立失败边界。

输入
计划要求的能力签名、固定目录、标准化参数、预算与取消信号，以及适配器返回的原始响应。
输出
带来源、新鲜度和状态的 SignalValue，或可解释的 Missing/Unavailable/Invalid 结果；业务判断不直接消费原始协议对象。

运行分支与交互

01计划解析能力描述

检查输入输出签名、权限、隔离域和兼容版本。目录标识解析到受控工厂，禁止让配置任意加载执行代码；描述缺失时在发布前拒绝计划。

02适配器需要初始化

使用独立生命周期协调连接、健康探测和资源释放。初始化可预热，也可按需，但失败要成为明确状态；不能让未初始化对象被当成正常空结果。

03能力接受执行请求

在剩余预算内排队与调用，区分读取和动作。参数按模式校验，返回携带实际执行者、耗时与请求关联标识；重试仅用于契约允许的操作。

04原始响应进入结果映射

先检查整体状态，再按声明提取字段、转换单位与类型、应用显式默认策略。一个字段缺失不应悄悄复用另一个字段；最终结果记录完整性和事实时间。

技术实现与取舍

把映射独立出来便于使用固定样例验证，也能支持能力协议演进。允许灵活映射的同时需要类型检查与资源限制，否则映射语言会变成未经治理的第二套执行引擎。

多个业务可共享底层连接，但能力描述和结果缓存按语义隔离。读取缓存应包含参数、事实时效与契约版本，不能只按能力名称取一份结果。

失败时会发生什么

  • 远端响应成功但字段单位变化，可能造成比网络异常更隐蔽的业务偏差。
  • 初始化失败被转换为空集合，会让上层把能力不可用理解为“没有资格记录”。
健康检查成功是否足以放行能力？

不足以。连接健康只覆盖技术通路，还需要契约样例、字段映射和权限验证；真实业务输入也可能触发不同分区与容量边界。

默认值为什么需要写进契约？

默认值就是业务判断的一部分。缺失金额用零和标记未知会导向不同结果，必须让编译器、调用者和审计者看到同一个定义。

CHAPTER 06

执行：就绪队列与取消的真实含义

依赖图描述什么必须先完成，调度器决定什么时候启动工作。通过就绪队列可以利用局部完成并发执行；通过明确终态可以避免重复扣减依赖和错误取消共享工作。

教学调度器为每个节点维护等待依赖计数与独立状态。只有已满足条件的节点进入就绪队列，完成事件推动后继；请求预算限制整个调度过程。调度顺序可以优化延迟，但不得改变规则的优先级和副作用语义。

参考设计

完成事件驱动的 DAG 就绪队列

节点可启动的条件是依赖语义满足，而不是“所有上游线程都结束了”。调度器要同时维护值、状态和执行所有权。

输入
固定执行子图、节点输入槽、资源配额、优先级提示与请求预算；外部完成事件可能重复或迟到。
输出
每个节点的一次终态转移、可解释的最终结果和完整执行轨迹；没有可运行工作时能够判断完成、阻断或图异常。

运行分支与交互

01初始化请求子图

只为选中节点建立依赖计数与输入槽，把无未满足依赖的节点放入就绪队列。请求输入也是显式已完成节点，避免到处增加“原始值特殊处理”分支。

02资源与预算允许启动就绪节点

原子把节点从 READY 改为 RUNNING 后提交，按能力类别使用独立配额。排队也消耗预算；提交失败返回调度状态，不能让节点永远停在 RUNNING。

03节点第一次进入终态

写入不可变结果槽，再通知后继。只有接受该结果的依赖边才扣减计数，后继达到条件后入队；重复回调看到节点已终态，不得再次扣减。

04上游失败或队列暂时为空

按边上的失败策略传播未知、选择兜底或阻断后继。队列为空但仍有运行任务时等待完成事件；既无运行任务又有未完成节点时，报告计划或状态机异常，而不是无限等待。

onComplete(node, result):
  if node.tryEnterTerminal(result):
    publishInputs(node, result)
    for edge in node.successors:
      if edge.accepts(result) and edge.satisfyOnce():
        enqueueIfReady(edge.target)

技术实现与取舍

就绪队列比全局分层屏障能更早释放局部后继，适合耗时差异大的节点；代价是状态机和并发协调更复杂。小图或高一致步骤可选择分层执行，结构简单本身也是优势。

关键路径优先有助于尾延迟，但优先级只是调度提示。公平性、隔离域配额与饥饿上限仍要约束，防止大型请求长期压住小请求。

失败时会发生什么

  • 完成回调重复扣减计数可能提前启动节点，产生读取尚未写入输入槽的竞争。
  • 把异常当普通值写入后继，或遇到失败直接停止所有节点，都会忽略计划中已经定义的兜底边。
计数归零为什么还需要节点状态比较？

计数只说明依赖条件，不说明是否已经被另一个线程提交。状态原子转移确保只有一个启动者，也让重复通知成为无害事件。

为什么不让工作线程直接递归执行后继？

深链会占用调用栈并绕过资源公平性，慢能力还会阻塞完成线程。完成线程负责发布事件，调度器统一控制何时提交下一项工作。

参考设计

取消：停止等待、停止调度与停止远端是不同动作

取消是合作协议，不是时间倒流。系统必须说明哪些工作尚可阻止、哪些正在尝试终止、哪些可能已经产生结果。

输入
调用方取消、请求预算耗尽、分支剪枝或系统资源保护信号，以及节点与共享工作的当前状态。
输出
尚未开始的工作不再提交，等待者得到一致终态；已经发生的外部动作进入可查询状态，迟到结果按明确政策处理。

运行分支与交互

01节点尚在等待或就绪队列

标记为取消并从可启动集合排除，唤醒等待其终态的依赖协调器。已经放入队列的句柄在真正提交前仍需再次检查，避免取消与启动之间的竞争。

02节点正在进行本地可中断计算

设置取消令牌，计算在安全检查点退出并释放资源。不得依赖强制终止线程来维护不变量；清理步骤使用独立的有限预算。

03节点正在等待远端或被多个请求共享

取消当前订阅并尽力传递协议级取消。只有没有其他消费者且执行者支持时才取消共享工作；远端不支持中止时允许其结束，但禁止迟到结果重新终结原请求。

04外部动作可能已经提交

取消不代表动作撤回。用动作标识查询已提交、未提交或状态未知，必要时执行明确补偿；不能在不确定状态下直接发起另一次等价动作。

技术实现与取舍

清晰取消语义可以控制资源浪费，也避免把用户停止等待解释为业务撤销。对读取可丢弃迟到值，对写入必须保留可核对状态；两者应使用不同端口。

过早取消共享缓存填充可能降低整体效率，完全不取消又可能浪费资源。共享协调器依据消费者数量、剩余成本和预热价值做决定，单个调用者只拥有自己等待的控制权。

失败时会发生什么

  • 把 Future 取消成功理解为远端未执行，会导致重复扣款、重复发券等不可逆错误。
  • 取消路径不让节点进入终态，会让图中的等待计数永远无法结束，形成请求已返回但后台资源泄漏。
超时后是否应该立即重试写入？

先依据幂等动作标识查询或使用同一标识重试。超时只说明没有及时得到结果，不说明远端没有接受；换新标识重试可能制造重复动作。

迟到读取结果可以进入缓存吗？

可以由独立缓存政策决定，但不能改变已经结束的请求。还要校验版本、时效与隔离域，避免把取消请求的无效数据注入共享状态。

CHAPTER 07

规则：明确结果归并，隔离外部动作

并发执行节点不应使决策取决于谁先返回。规则优先级、保护约束与副作用分别建模，才能既解释结果，又控制重复执行。

教学场景同时存在资格规则、人工保留约束和活动预算约束。某条规则“命中”只产生候选证据，DecisionReducer 再按声明的代数归并；外部发券由独立动作流水执行。判断与动作分离让影子评估和回放不会意外改变真实世界。

参考设计

保护优先级与确定性的结果归并

优先级必须定义冲突如何解决；不能把列表排序或完成顺序当作完整业务语义。保护范围、覆盖权与证据都应进入归并规则。

输入
各规则的候选结果、证据、适用范围与强度，以及请求所属场景的归并政策。
输出
唯一领域决策、决定性证据与被覆盖候选的解释；同一候选集合无论以什么完成顺序输入，都得到相同结果。

运行分支与交互

01规则产生候选结论

附带规则标识、版本、范围、证据完整性与建议动作，而不是直接修改全局决策。评估异常产生不可用状态，不能伪造成未命中。

02候选中存在保护或强制约束

先检查其覆盖范围与授权来源。保护可能只屏蔽某类动作，不自动抹去所有审计证据；强制限制也不能被普通允许规则覆盖。

03多个同范围候选冲突

使用显式且稳定的归并规则，例如先比较约束级别，再比较声明优先级，最后采用确定性平局规则。并行完成先后不参与业务排序。

04必要证据缺失或只有影子候选

按政策返回补充信息、受限允许或其他明确状态。影子候选仅进入比较记录，不改变真实决策，也不能触发外部动作。

技术实现与取舍

若归并操作满足交换、结合和幂等性质，就能更自由地并发与重放；无法满足时要保留显式顺序并解释原因。性能优化不能偷换业务的顺序语义。

短路仅在剩余规则无法改变最终结果时成立。即使判断可短路，审计必需规则是否继续执行也应独立配置，否则结果正确却缺少必须保存的依据。

失败时会发生什么

  • 规则直接写共享结果变量，会把线程调度顺序变成隐藏优先级。
  • 把保护理解成无条件放行，可能覆盖它本来无权覆盖的约束；范围与权限必须与保护一起建模。
排序后取第一个命中是否足够？

只适用于业务明确规定首个命中的情况，仍需说明保护、强制约束和异常如何参与。一般冲突更适合用可检查的归并模型表达。

如何验证并发没有改变规则结果？

固定候选集合，随机排列完成事件并做归并性质检查；再覆盖缺失证据、保护范围冲突和短路情况。测试应检查业务不变量，而不是复刻排序代码。

参考设计

副作用：先记录意图，再按幂等协议执行

决策可以重算，外部动作可能不可逆。把动作从判断中分离，用稳定业务身份和持久化状态抵御重试与结果未知。

输入
已经归并的决策、允许产生的动作意图、稳定业务标识，以及外部系统提供的幂等或状态查询契约。
输出
可跟踪的动作流水：待执行、已确认、失败或结果未知；请求响应不依赖把所有后续动作同步完成。

运行分支与交互

01决策需要发券等外部动作

构造 EffectIntent，包含业务主体、动作种类、语义参数与决策证据。幂等键表示同一业务意图，不能简单使用每次随机生成的请求标识。

02意图进入持久化边界

把决策记录与 outbox 意图放进可保证一致的提交过程；若无法共享事务，定义补偿和对账协议。提交失败不能向调用者宣称动作已经可靠受理。

03EffectWorker 尝试执行

按动作键取得执行权，向远端传递相同幂等身份。成功后记录远端凭据；确定失败才按政策重试，不把所有超时都视作未执行。

04状态未知、重复投递或业务撤销

重复投递返回现有流水，未知状态先查询核对；撤销生成独立补偿意图。补偿也可能失败，需要自己的幂等键与状态机，而不是直接删除原流水。

intent = EffectIntent.forBusinessOperation(decision, operationIdentity)
commit(decisionRecord, outbox.appendIfAbsent(intent))
worker.executeWithStableIdentity(intent)
worker.reconcileUnknownOutcome(intent)

技术实现与取舍

outbox 提高提交与异步派发的可靠性，但不凭空实现跨系统恰好一次。远端支持幂等是理想条件；不支持时需要去重窗口、状态核对或业务上可接受的重复处理策略。

幂等键需要说明作用域和参数一致性。同键带不同参数时应拒绝冲突，不能静默返回第一次结果；键的保留期限还要覆盖业务可能重试的时间范围。

失败时会发生什么

  • 先调用外部动作再写本地记录，进程崩溃后无法判断是否已执行。
  • 为每次重试生成新幂等键，会让去重协议形同虚设；永久复用过宽的键又会错误吞掉后续合法动作。
outbox 是否保证动作不会重复？

它保证持久化意图有机会被可靠派发，派发仍可能重复。动作端需要识别同一业务意图，或通过状态核对获得可接受语义。

回放为什么不能复用正常动作通道？

回放用于验证决策，应把 EffectIntent 写入隔离记录或直接禁止执行。仅更换展示标记不足以阻止真实动作，执行权限要在动作边界明确分开。

CHAPTER 08

推演：用故障验证承诺，而不是只看成功路径

架构说明最终应落到可证伪的问题：新版本失败时读者看到什么，远端迟到时动作会不会重复，取消后后台资源是否收敛。故障演练把这些承诺变成可检查结果。

选择可观察的不变量，再注入故障。仅看到请求仍能返回并不能证明设计成立：它可能采用了错误默认事实、遗漏动作或混合版本。诊断记录应连接请求、计划摘要、能力结果和动作身份，但不把敏感原文直接当作日志标签。

本章给出独立教学验收方法。每项都需要在可控环境使用模拟能力与隔离动作端点执行；实际系统是否满足这些性质，应由其自身的测试与运行证据回答。

参考设计

围绕版本、预算和动作状态做故障推演

有价值的演练先声明不变量，再检查故障前后状态；“没有报错”或“平均延迟正常”不能代替正确性证据。

输入
固定请求样本、候选版本、可控时钟、可注入失败的能力适配器与隔离动作接收端，以及事先写下的验收不变量。
输出
可复查的执行时间线、版本与动作状态证据，以及通过或失败的具体不变量；发现差异后能够定位到边界而非只归类为系统异常。

运行分支与交互

01候选计划构建到一半时注入失败

确认当前根未变，旧请求能够完成，新请求仍获取完整旧版本。随后修复输入并重新发布，检查是否只出现完整的新根，且没有依赖通知到达顺序才能恢复。

02大量请求同时遇到冷表达式与慢能力

检查同键编译是否合并、不同键并发是否受限，等待者期限是否独立。让部分请求取消，确认其他订阅不被误杀，资源在所有请求结束后回到可解释状态。

03远端动作接受后延迟响应，再让执行进程重启

使用相同动作身份重试或查询，验证接收端只承认同一业务意图，并保留结果未知到确认的证据。动作没有幂等契约时，演练应明确暴露这个限制。

04规则并发顺序、事件重复和事实缺失被扰动

对同一候选集合交换完成顺序，确认归并结果不变；重复通知不产生额外发布，丢通知能由对账恢复。事实缺失应表现为契约中的未知或降级状态，不能静默变成否定事实。

技术实现与取舍

把正确性指标与可用性指标并列：固定版本是否完整、响应是否唯一终结、动作状态是否可核对、取消后工作是否收敛。延迟和吞吐仍重要，但不能掩盖错误结果。

演练规模由风险和代表性决定，先验证状态机边界再增加负载。持续扩大压力无法替代覆盖关键竞争：发布与读取、取消与完成、重试与远端提交、缓存驱逐与句柄使用。

失败时会发生什么

  • 只统计错误率，会把按错误默认值得到的“成功响应”遗漏掉。
  • 只验证最终结果、不保留时间线，可能看不到曾经暴露的中间态；只保留时间线而没有不变量，又难以判断什么属于失败。
哪些证据足以说明发布成功？

候选验证摘要、根切换记录以及目标读者实际持有的版本报告需要相互对应。配置源写入成功或通知发送成功，只证明链路中的一个阶段。

演练暴露限制后应如何表达结论？

写明测试条件、观察到的状态与未覆盖范围。例如“重复投递可去重，但远端不支持结果查询时仍会存在未知状态”，比笼统宣称可靠或不可靠更可用于决策。
